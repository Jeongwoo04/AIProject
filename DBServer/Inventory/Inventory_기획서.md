# Inventory 시스템 기획서

## 1. 목적 및 범위

Player가 소유한 Item Instance를 슬롯 단위로 보관하고, 아이템 획득·조회·이동·사용·제거 및 장비 시스템과의 연동을 관리한다.

구현 대상은 Player Inventory와 GameServer에서 Inventory를 변경하는 요청 및 처리다. 아이템의 정의와 `Item::Use()` 세부 동작은 `Item_기획서.md`를 따른다.

### 1.1 획득 경로
- 월드 드랍 루팅
- 게임 보상
- 상점 구매
- 교환

### 1.2 제외 범위
- NPC Inventory
- Item Definition 자체의 설계
- 캐릭터 능력치 계산
- DBServer 내부 구현
- 몬스터 DropTable의 상세 확률 정책

단, Inventory 연동에 필요한 인터페이스와 저장 시점은 정의한다.

## 2. 소유 관계 및 GameServer 연동

- Player가 Inventory를 소유한다.
- Inventory는 보관 중인 Item Instance를 소유한다.
- Player가 ObjectManager를 통해 생성될 때 Inventory를 초기화한다.
- Player 제거 과정에서 Inventory와 소유 Item Instance를 정리한다.
- DB 저장은 Player/Inventory 소멸자에서 직접 수행하지 않고 명시적인 저장 절차에서 처리한다.
- 클라이언트 슬롯 요청(예: `C_ItemMoveReq`)은 GameServer에서 Player 소유권, 슬롯 인덱스 및 요청 조건을 검증한 뒤 Inventory 변경 함수로 전달한다.
- Inventory는 Item 시스템의 Item Instance를 보관하고, Item 사용 결과에 따라 수량과 슬롯 상태를 갱신한다.

## 3. 슬롯 및 적재 정책

- 최대 슬롯 수는 40칸이다. 클라이언트 표기는 8×5이며 서버는 0부터 시작하는 1차원 인덱스로 관리한다.
- 클라이언트가 보낸 슬롯 인덱스는 서버에서 범위 검증한다. 클라이언트 표기와 서버 인덱스 변환 규칙은 일치시킨다.
- 고정 크기 슬롯 배열을 사용하고 슬롯 인덱스로 직접 조회한다. 빈 슬롯은 배열 순회로 찾는다. 현재 40칸 규모에서는 별도 FreeList를 필수로 두지 않는다.
- `ItemDefinitionID`가 같은 Item Instance를 중첩 후보로 판단한다. 실제 중첩 한도는 Item 기획서의 `MaxStackCount`를 따른다.
- 기존 중첩 가능 슬롯을 먼저 채운 뒤 남은 수량을 빈 슬롯에 배치한다.

### 3.1 공간 부족 정책

- **월드 드랍 루팅:** 들어갈 수 있는 수량만 적재하고 남은 수량은 월드 드랍 객체가 유지한다. 하나도 적재할 수 없으면 루팅 실패다.
- **보상·구매·교환:** 전체 적재 가능 여부를 사전에 확인한다. 공간이 부족하면 작업 전체를 실패 처리하며 재화 또는 교환 대상 아이템을 변경하지 않는다.

## 4. 주요 기능 및 처리 정책

### 4.1 획득 및 적재
- 루팅·보상·구매·교환 요청은 서버에서 획득 조건을 검증한 후 적재를 시도한다.
- 기존 중첩 슬롯을 우선 사용하고 이후 빈 슬롯을 사용한다.
- 적재 결과는 성공/실패 및 실제 적재 수량을 호출 측에 반환한다.
- 보상·구매·교환은 전체 적재 가능 여부를 먼저 확인한 뒤 관련 재화/아이템 변경과 Inventory 적재를 함께 처리한다. 부분 처리로 결과가 불일치하지 않도록 한다.

### 4.2 조회 및 사용
- Item Instance는 슬롯 인덱스로 조회한다.
- 사용 요청은 해당 Player 슬롯에 Item Instance가 존재하는지 확인한 뒤 Item의 사용 인터페이스를 호출한다.
- 사용 성공 후 수량을 반영하고 Count가 0이 된 Instance는 슬롯에서 제거한다.
- 사용 실패 시 Inventory의 수량과 슬롯 상태는 변경하지 않는다.

### 4.3 이동, 중첩 및 제거
- 출발·도착 슬롯의 인덱스 범위를 검증한다.
- 도착 슬롯이 비어 있으면 Item Instance를 이동한다.
- 동일 Definition이면 최대 중첩 수량까지 합치고 잔여 수량을 처리한다.
- 서로 다른 아이템이면 두 슬롯을 교환한다.
- 이동·합치기·교환은 결과를 사전 검증한 뒤 반영하며 실패 시 요청 전 슬롯 상태를 유지한다.
- 드랍은 서버가 가능 여부와 수량을 검증한 뒤 월드 드랍 객체를 생성하고 Inventory에서 수량을 제거한다. 월드 객체 생성에 실패하면 Inventory를 변경하지 않는다.
- 판매·교환 등 기타 제거는 거래 조건과 결과를 검증한 뒤 수행하며, 거래 실패 시 Item을 유지한다.

### 4.4 장비 연동
- 장비 슬롯은 Inventory와 별도의 Equipment 또는 Character 장비 관리 컴포넌트가 관리한다.
- 장착 중인 Item Instance의 소유 위치는 Equipment이며 Inventory 슬롯과 동시에 소유하지 않는다.
- 장착 성공 시 Item Instance를 Inventory 슬롯에서 Equipment 슬롯으로 이동한다. 기존 장착 아이템이 있다면 교체 결과를 먼저 검증한다.
- 해제 시 Equipment의 Item Instance를 Inventory의 빈 슬롯에 반환한다. 빈 슬롯이 없으면 해제 실패로 처리하고 장착 상태를 유지한다.
- 장착/해제에 따른 HP·MP·Attack 적용 및 계산은 Character의 책임이며 Inventory는 Item Instance의 위치 변경을 담당한다.

## 5. 검증 및 실패 처리 정책

- 요청 Player의 소유권, 슬롯 인덱스, Item Instance 존재 여부, 수량, 적재 공간 및 기능별 조건을 서버에서 검증한다.
- 중복 요청으로 아이템이나 재화가 중복 변경되지 않도록 요청 식별 또는 처리 상태 기반의 중복 방지 정책을 거래·보상·저장 경로에 적용한다.
- 여러 슬롯 또는 재화와 Item을 함께 변경하는 작업은 사전 검증 후 반영하며 실패 시 변경 전 상태를 유지한다.
- 조회 실패, 공간 부족, 조건 불일치 및 처리 실패는 클라이언트에 실패 결과를 전달하고 서버 로그에 원인과 요청 종류를 기록한다.
- 한 Player의 Inventory 변경은 GameServer의 해당 Player 처리 흐름에서 직렬화한다. 실행 모델이 이를 보장하지 않으면 별도 동기화가 필요하다.

## 6. 완료 기준

- Player 생성 시 Inventory가 초기화되고 Player 제거 시 Item Instance가 정리된다.
- 40개 슬롯 및 인덱스 경계(최솟값·최댓값·범위 초과)를 검증한다.
- 획득, 중첩, 부분 적재, 공간 부족, 조회, 사용, 이동, 교환, 드랍 및 제거가 성공/실패 조건에서 올바르게 동작한다.
- 장착/해제 시 Item Instance가 Inventory와 Equipment 사이에서 중복 소유되거나 유실되지 않는다.
- 보상·구매·교환 실패 시 Inventory 및 재화 상태가 변경되지 않는다.
- 중복 요청 및 변경 실패 상황에서 Item 수량·슬롯·재화의 일관성이 유지된다.
- 로그는 성공/실패와 실패 원인을 확인할 수 있어야 한다. 로그 출력만이 아니라 상태 검증 테스트를 완료 기준으로 삼는다.

## 7. 확정 및 조율 사항

- 슬롯 수는 40칸(클라이언트 8×5)으로 하고 서버는 1차원 인덱스로 관리한다. 클라이언트 인덱스 시작값과 2D→1D 변환식은 Packet 정의와 함께 확정한다.
- Player 생성 시 Inventory를 생성하고 Player 제거 시 정리한다. DB 저장은 소멸자에서 직접 쿼리하지 않고 별도 저장 흐름으로 수행한다.
- 몬스터 DropTable은 Item Definition ID와 확률을 기반으로 월드 드랍 생성 시스템에서 처리하고 Inventory는 루팅과 적재를 담당한다.
- Gold는 Item 슬롯과 분리된 Player 재화 데이터로 관리하는 방향을 권장한다. 초안에는 Inventory의 Gold 멤버를 초기 구현 대안으로 제시했으므로 실제 소유 위치는 구현 전 확정이 필요하다.
- DB 저장 방식은 GameServer가 변경 성공 시점에 DBServer로 명시적 저장 요청을 보내는 대안을 제시한다. 비동기 응답, 요청 순서, 중복 처리 및 실패 재시도 정책은 DBServer 연동 명세에서 구체화한다.
- 40칸 규모에서는 빈 슬롯 배열 순회를 유지하고 FreeList는 도입하지 않는 방향이다.
- 월드 드랍은 부분 적재, 보상·구매·교환은 전체 적재 성공 정책을 사용한다.
